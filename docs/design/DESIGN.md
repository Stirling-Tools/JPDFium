# Native design

One document for the safe native API: architecture, ABI, lifetime, binding
concurrency, capabilities, the raster and text-layer contracts, the optional
OCR module, and test evidence. The Java migration notes live separately in
[JAVA_MIGRATION.md](JAVA_MIGRATION.md).

## Native-first architecture

Status: accepted for the PyJPDFium first pass. Supersedes the resident-JVM/IPC default for Python.

## Decision

JPDFium's native library owns PDFium serialization, lifecycle, handle validation and memory
ownership. Java (FFM) and Python (nanobind, in the PyJPDFium repository) are peer bindings over
one safe C API, `native/bridge/include/jpdfium_api.h`. Python needs no JVM.

Native-first buys deployment simplicity and one implementation. The core runs inside the host
process; jobs that need their own memory or time limits can run in an optional worker process.

```text
Java API (FFM)            Python API (nanobind, PyJPDFium)
        \                      /
         safe jpdf_* C API (jpdfium_api.h)
           runtime domain . object table . output transactions
                       |
             libjpdfium (one core) + PDFium + Rust helpers
```

## Single core

The domain, the object table and PDFium itself live in `libjpdfium` only. Bindings and future
optional modules (OCR) link to it dynamically and must never compile their own copy, or two
libraries would each believe they are the only serializer.

Java reaches PDFium only through `jpdf_guard_*` shims (generated by `native/tools/gen_guards.py`),
which admit each legacy `jpdfium_*` or raw PDFium call to the same native domain the safe API
uses. Java holds no lock of its own. The legacy `jpdfium_init*` entry points remain for raw ABI
users; the first of `jpdfium_init*` or `jpdf_runtime_init` claims PDFium for the process, and the
other is refused, so an unguarded legacy caller can never run beside the domain.

## Safe native ABI

The contract for `native/bridge/include/jpdfium_api.h`. The legacy `jpdfium.h` ABI is unchanged
and keeps raw pointer-valued handles; the two surfaces never share handle values.

## Versioning

`jpdf_api_version()` returns `(major << 16) | minor`. A binding accepts the library when the
major matches and the minor is at least the one it was compiled against. Additive changes bump
the minor; any layout or semantic break bumps the major. 1.1 added rasterization and
rectification; 1.2 added page text and text layers; 1.3 added PNG loading and the module
interface below; 1.4 added quads and base directions to text lines and words.

`jpdf_abi_struct_size(JPDF_STRUCT_*)` reports each struct's size so bindings that do not compile
against the header (Java FFM) can verify layouts at load time.

## Structs

Every struct starts with `uint32_t struct_size`, uses fixed-width fields and explicit `reserved`
padding, so the layout is identical on every 64-bit target.

Input structs (`*_options`):

- `struct_size` below the 1.0 size is `JPDF_E_INVALID_ARGUMENT`.
- A larger struct from a newer caller is accepted only when every byte the library does not know
  is zero; otherwise `JPDF_E_UNSUPPORTED`. A newer caller can never silently lose a setting.
- Unknown flag bits and non-zero reserved fields are `JPDF_E_UNSUPPORTED`.
- A `NULL` options pointer selects documented defaults where the function allows it.

Output structs (`*_info`, `jpdf_bitmap_view`): the caller sets `struct_size`; the library
requires at least the 1.0 size and never writes past `struct_size`.

Arrays of structs (`jpdf_text_line`, `jpdf_text_word`) are read with the first element's
`struct_size` as the stride. Every element must carry that same size, which must keep elements
8-byte aligned; each element is then checked like an input struct. Their 1.0 size is the 1.3
layout, before the quads; fields past an element's `struct_size` read as zero.

Native structs are not a wire format. Do not serialize them across processes.

## Strings

Inputs are NUL-terminated UTF-8. Library-owned output strings (`build_id`, status names) are
static. Error detail (`jpdf_last_error_message`) and page text (`jpdf_page_get_text`) are copied
into a caller buffer: `required` includes the NUL, a NULL buffer only reports it, and a short
buffer is `BUFFER_TOO_SMALL` with `required` still set.

## Status codes

Every function returns `jpdf_status`; `JPDF_OK` is 0 and every failure is negative. Bindings must
map unknown negative values to an internal error, never to success.

| Status | Meaning |
|---|---|
| `INVALID_ARGUMENT` | Bad plain argument or struct |
| `INVALID_HANDLE` | Token was never issued, or is malformed |
| `STALE_HANDLE` | Token was valid once and has been closed |
| `WRONG_HANDLE_TYPE` | Token is live but of another type |
| `BUSY` | Close or shutdown refused while dependents exist; nothing changed |
| `UNSUPPORTED` | Unknown flag, option, field or format |
| `IO`, `PASSWORD`, `FORMAT`, `NOT_FOUND` | Input problems |
| `LIMIT` | Pixel or byte budget exceeded |
| `NO_MEMORY`, `BUFFER_TOO_SMALL` | Allocation or caller buffer too small |
| `NOT_INITIALIZED`, `QUIESCING`, `STOPPED`, `FAILED` | Runtime state refuses the call |
| `AUTHORITY` | The legacy bridge already owns PDFium in this process |
| `REENTRANT` | Called from inside the domain |
| `CANCELLED`, `TIMEOUT` | Reserved |
| `INTERNAL` | Unexpected native failure |
| `UNSYNCED` | Destination was replaced, but the durability sync failed: the new bytes are visible, their crash durability is uncertain |

Detail is per thread and per call: each call clears it, and the first failure in a call wins so
cleanup cannot overwrite the cause. Read it before making another call on the same thread.

## Ownership

| Value | Ownership |
|---|---|
| Path, password, options | Borrowed for the duration of the call |
| Text layer lines, words and their strings | Borrowed for the duration of the call |
| Document, page, bitmap, view tokens | Owned by the caller until the matching close or release |
| Bitmap pixels | Owned by the library; independent of the page and document |
| `jpdf_bitmap_view.data` | Valid until `jpdf_view_release`, even after the bitmap closes |
| `build_id`, status names | Static, owned by the library |
| Error detail | Copied into the caller's buffer |

## Optional modules

`jpdfium_api.h` (module section) lets an optional native module, such as the OCR module, keep its objects in the
core's generation-checked table instead of a table of its own. A module inserts an object with a
non-zero kind and a destroy function. It takes a lease for the length of each call that uses the
object, and closes the handle when the caller does. A handle of another kind is
`WRONG_HANDLE_TYPE`. The object is destroyed once its handle is closed and no lease remains.

A module entry point starts with `jpdf_module_begin_call` and records failures with
`jpdf_module_fail`, so callers read its errors with `jpdf_last_error_message`. The other module
functions keep the recorded detail, so cleanup cannot overwrite it. A module must stay loaded while
its objects exist.

## Legacy guards

`jpdf_guard_<name>` exists for every legacy `jpdfium_*` export except the QPDF, Rust, ABI-probe
and legacy-init functions, and for every PDFium symbol the Java bindings use. Each has the
signature of `<name>`. A refused admission returns a zero value (or nothing for `void`) without
running `<name>`; `jpdf_guard_take_refusal()` then returns the status for the calling thread and
clears it. Bindings must check it after every guarded call, because a zero `int32_t` status is
indistinguishable from `JPDFIUM_OK`.

No C++ exception crosses the ABI: every entry point is `noexcept` and runs its body inside an
exception firewall that maps failures to status codes. The generated guards keep that guarantee
without a catch boundary of their own: each wrapped `jpdfium_*` function is itself `noexcept` or
catches every exception internally, and the raw PDFium symbols are C functions that cannot throw
across this frame. The guard's only added work is atomic lifetime accounting, which does not
allocate and cannot throw.

A small, fixed set of raw PDFium factories and their matching closes carry the same lifetime
accounting as the bridge: `FPDF_CreateNewDocument`, `FPDF_ImportNPagesToOne` and `FPDFPage_New`
record an open document or page when they return a non-null handle, and `FPDF_CloseDocument` and
`FPDF_ClosePage` record the matching close. So a document or page created through the raw bindings
still keeps `jpdf_runtime_shutdown` returning `JPDF_E_BUSY` until it is closed through the matching
raw close. Objects the bridge creates are counted once, by the bridge, because the bridge calls
PDFium directly and never through these guards.

## Runtime, handle and resource lifetime

## Runtime states

```text
UNINITIALIZED --init--> RUNNING --quiesce/shutdown--> QUIESCING --> DESTROYING --> STOPPED
                                                                              \--> FAILED
```

- `jpdf_runtime_init` is explicit lazy initialization. Bindings call it on first use; importing a
  binding loads nothing. Calling it again while running is a no-op.
- Closing a document never shuts the runtime down. The runtime normally lives for the process.
- `jpdf_runtime_quiesce` stops admitting ordinary work. Closing existing pages and documents is
  still allowed.
- `jpdf_runtime_shutdown` quiesces, then destroys PDFium only when no documents or pages remain.
  Otherwise it returns `JPDF_E_BUSY` with the counts and stays `QUIESCING` so the caller can
  close what is open and retry.
- `jpdf_runtime_resume` returns `QUIESCING` to `RUNNING`, for callers that abandon a shutdown.
- `jpdf_runtime_shutdown_within(ms)` gives up with `JPDF_E_TIMEOUT` if the domain stays busy, so
  an exit hook never waits behind a long operation.
- `STOPPED` and `FAILED` are terminal for the process. There is no silent reinitialization.

## Admission

Every entry point that touches PDFium follows one sequence:

```text
validate plain arguments -> admit -> resolve handles -> execute PDFium work -> leave -> return
```

`jpdf::Admission` is an RAII guard over the single domain mutex. A refused admission holds nothing;
a granted one is released exactly once by its destructor, on every return and exception path.
The runtime state is checked inside the mutex, so admission and shutdown cannot interleave.

The mutex is not recursive. Internal helpers run under the caller's admission and never admit
again; a public entry point reached from inside the domain gets `JPDF_E_REENTRANT` instead of a
deadlock.

Legacy entry points are admitted the same way through their `jpdf_guard_<name>` shim, one call
per admission. Close and free functions are teardown and stay admitted while quiescing. A refused
shim returns a zero value and records the status for `jpdf_guard_take_refusal`, which bindings
check after every guarded call.

Only PDFium work runs admitted. Pixel conversion, PNG encoding and file publication run after
leaving the domain, and bitmap operations never enter it.

## Handles

A `jpdf_handle` is an opaque 64-bit token: object type, slot generation and slot index. Before any
dereference the table checks that the token was issued, its type matches, its generation matches
the slot and the object is still live. A slot whose generation would wrap is retired permanently,
so no stale token can become valid again.

## Close policy

- Close is idempotent at the binding level; natively a second close is `JPDF_E_STALE_HANDLE`.
- Children retain parents: a page holds a reference to its document.
- Closing a document with open pages is `JPDF_E_BUSY` and leaves the document fully usable.
- PDFium objects are destroyed only while admitted. Object destructors never call PDFium.
- There is no cascading close and no close from destructors in native code.

## Bitmaps and views

A render produces an independently owned bitmap: closing its page or document does not affect it,
and it survives runtime shutdown. `jpdf_bitmap_map` returns a view that pins the pixels; the
pointer stays valid until `jpdf_view_release`, even if the bitmap handle is closed first. Pixels
are immutable after publication, so views need no locking.

## Output transactions

`created -> writing -> finalized -> validated -> published`, or `aborted` on any failure.

- The staging file is created exclusively, without following links, beside the
  symlink-resolved destination, so publication is a same-directory rename.
- Output is bounded by `max_bytes`; exceeding it aborts mid-write.
- Publication is atomic replacement only (`rename(2)`, `MoveFileExW`). There is no non-atomic
  fallback; a refused rename fails the operation and leaves the destination untouched.
- `JPDF_WRITE_DURABLE` adds fsync of the file and its directory. It is a separate policy from
  atomicity.
- A pre-publication failure removes the staging file and leaves the destination unchanged.
- A successful call reports one of three outcomes, never conflated into "nothing changed": a
  non-zero status before publication means the destination was not replaced; success means the
  destination holds the new bytes and, with `JPDF_WRITE_DURABLE`, that they are durable; and
  `JPDF_E_UNSYNCED` means the rename already replaced the destination but the directory sync failed,
  so the new bytes are visible while their crash durability is uncertain. Callers must not assume a
  non-zero status always means no external change.

## Callbacks and binding concurrency

## Policy

No Java or Python application code runs while the PDFium domain is held by the 1.0 safe API, which
has no application callbacks at all. Future progress or cancellation uses polled state (atomic flags,
buffered events), not upcalls. The legacy save path is the exception: the `FileWriteSink` upcall
writes to a caller `OutputStream` while a guarded save holds the domain (see Java below).

Native-to-native callbacks are allowed when they cannot re-enter the API, for example the PNG
encoder's byte sink, which writes into an output transaction outside the domain.

## Locks never span managed code

The domain is acquired and released inside one native call. A binding must not expose
`enter()`/`exit()` downcalls that bracket arbitrary Java or Python code. When an atomic batch is
needed, add a coarse native operation instead.

## Python GIL sequence

```text
GIL held:     validate arguments, convert inputs to native values
GIL released: run the jpdf_* call (admission, PDFium work, leaving the domain)
GIL held:     read error detail, build the result or raise the mapped exception
```

No Python object is touched while the GIL is released. Because the domain is always released
before the GIL is reacquired, a thread waiting for the GIL can never hold the domain, so the two
locks cannot deadlock.

## Java

Java holds no PDFium lock; every PDFium call is a guarded native call. Two binding-internal
upcalls still run while a guarded PDFium call is in progress: the `FPDF_FILEWRITE` sink behind
`FileWriteSink` (it writes to a caller `OutputStream`) and the JPEG `GetBlock` reader in
`PdfImageOptimizer`. Neither calls PDFium; if one did, its guard would refuse with
`JPDF_E_REENTRANT` instead of deadlocking. Moving the save sink to the native file writer is a
listed follow-up in [JAVA_MIGRATION.md](JAVA_MIGRATION.md).

## Raster contract for OCR pipelines

`jpdf_rasterize_page_file` implements OCRmyPDF's `rasterize_pdf_page` hook natively. The reference
is OCRmyPDF 17.13.0's pypdfium rasterizer (`builtin_plugins/pypdfium.py`) on pypdfium2 5.14.0,
with Ghostscript's behaviour as the tie-breaker where the two disagree.

## Matched behaviour

- Raster DPI is rounded to 6 decimals (Python `round(x, 6)`).
- The expected size is `round(points * dpi / 72)` with Python's half-to-even rounding.
- The page is rendered at `ceil(points * dpi / 72)`, then a 1-2 px overshoot is trimmed and the
  image is cropped or white-padded to the expected size when either axis is within 2 px. Nothing
  is resampled.
- Gray and mono devices render into an 8-bit gray PDFium bitmap with `FPDF_GRAYSCALE`; others
  render packed BGR. Annotations are drawn (`FPDF_ANNOT`); form fields are not separately drawn,
  because the reference never initializes a form environment.
- By default the CropBox is widened to the MediaBox in memory before rendering.
- Mono output uses Pillow's Floyd-Steinberg integer arithmetic (`Image.convert("1")`), bit for
  bit.
- DPI metadata is the output DPI if given, otherwise the raster DPI, written as Pillow writes
  pHYs: `int(dpi / 0.0254 + 0.5)` pixels per metre.
- Output is published through an output transaction: a failure never leaves a partial PNG.

## Devices

| OCRmyPDF device | Output |
|---|---|
| `pngmono`, `pngmonod` | 1-bit gray PNG |
| `pnggray` | 8-bit gray PNG |
| `png16m` | 24-bit RGB PNG |
| `pngalpha` | 24-bit RGB PNG; the reference renders on opaque white, so it never carries alpha |
| `png256` | 24-bit RGB PNG (deviation below) |
| `jpeg`, `jpeggray`, `tiff` | Rejected: the core has no JPEG or TIFF encoder |

## Intentional deviations

Each is pinned by a parity test that asserts both the reference's output and ours.

| Case | Reference | Ours, and why |
|---|---|---|
| Rotation on a page with its own `/Rotate` | Overwrites `/Rotate` with the correction | Adds the correction to `/Rotate`, as Ghostscript does |
| Non-square raster DPI | Renders both axes at the harmonic mean, so the image and its DPI disagree | Renders each axis at its own DPI, as Ghostscript does |
| CropBox smaller than MediaBox on one axis only | Crops the MediaBox render to the CropBox size from its top-left corner | Keeps the full MediaBox render; the expected size comes from the box actually rendered |
| Quarter-turn correction | Keeps the DPI axes | Swaps the DPI axes with the image, as Ghostscript does |
| `png256` | Median-cut palette quantization | RGB; quantization only loses information OCR could use |
| `filter_vector` | Silently ignored | Rejected with `JPDF_E_UNSUPPORTED` |

With square DPI, no page `/Rotate` and matching boxes (the usual case), sizes, modes and DPI are
identical to the reference.

## Measured parity

Linux x86-64, pinned PDFium against pypdfium2 5.14.0's PDFium, for a vector page, a Helvetica
text page and a 256-step gray ramp at 72, 150 and 300 dpi, unrotated and with a quarter turn:
sizes, modes and DPI are identical; pixels are identical for every case except RGB text, where at
most 0.27% of samples differ (mean difference 0.003 of 255) because the two PDFium builds
anti-alias glyph edges slightly differently. Gray and 1-bit text are identical.

The parity suite lives in PyJPDFium (`tests/parity`); it runs the reference in a separate process
from hash-pinned sources.

## Rectification

`jpdf_bitmap_rectify` perspective-corrects a quad from a bitmap: corners in any order are reordered
top-left, top-right, bottom-right, bottom-left; collinear, concave, non-finite and sub-pixel quads
are rejected; the default output size is PaddleOCR's truncated length of the longer opposite
edges; sampling follows OpenCV's `warpPerspective` geometry (pixel centres on integers) with
nearest, bilinear or OpenCV-cubic interpolation and a white or replicated border. The result
carries the homography from output pixels back to source pixels. Interpolation is computed in
floating point, so it is close to but not bit-identical with OpenCV's fixed-point tables.

## Invisible text layers

`jpdf_text_layer_write` writes the text-only PDF that OCRmyPDF's `generate_pdf` hook returns for
its sandwich renderer: one page, sized to the OCR image, holding invisible text and nothing else.
It never touches PDFium, so it runs outside the domain and in any runtime state.

## Input

- The page is `image_width / dpi_x * 72` by `image_height / dpi_y * 72` points.
- Lines come in reading order. Each has a box and takes the next `word_count` words from the word
  array. Words carry UTF-8 text in logical order and a box. Boxes are image pixels, origin
  top-left.
- A line without word geometry is passed as one word holding the whole line, spaces included.
  The writer never invents word boxes by dividing a line.
- Since API 1.4 a line or word may carry a quad instead of a box (`JPDF_TEXT_LINE_QUAD`,
  `JPDF_TEXT_WORD_QUAD`): corners top-left, top-right, bottom-right, bottom-left as read. Text
  runs along the top-left to top-right edge, so OCR polygons of rotated or skewed lines keep
  their slope. Callers built against 1.3 pass the shorter structs and get the 1.3 behaviour.
- A line's base direction comes from its first strong character, or from `JPDF_TEXT_LINE_LTR`
  or `JPDF_TEXT_LINE_RTL`. Words stay in logical order whatever the direction.

## Layout

The layout follows OCRmyPDF 17.13's renderer (`fpdf_renderer/renderer.py`):

- One `BT ... ET` block per line in render mode 3 (invisible), with a `Td` and a `Tz` per word.
- The font size is the line height. The font's ascent and descent (800 and -200) add up to one
  em, so glyph boxes cover the line box exactly; the baseline sits a fifth of the line height
  above its bottom.
- `Tz` stretches each word to its box width.
- Every word is followed by a space character, line-final words included, so extractors without
  layout analysis still separate words. Between two CJK words no space is written; the first is
  stretched to meet the second when the gap is at most two ems.

Left-to-right lines with boxes are written exactly as above. Other lines take the general path
below.

### Right-to-left and mixed text

Each word is laid out with ICU's implementation of the Unicode bidi algorithm (UAX #9), at the
line's base level. Characters stay in logical order in the content stream, and each directional
run gets its own text matrix: left-to-right runs advance rightwards, right-to-left runs are
mirrored (`-1` horizontal scale) and advance leftwards from their right edge. Each character
lands in the cell the bidi algorithm gives it, so:

- extractors that read stream order (pdfminer.six) get logical text directly;
- extractors that rebuild order from positions (PDFium, poppler) see an ordinary right-to-left
  line and reverse it back to logical text.

Tesseract's PDF renderer uses the same mirrored layout for right-to-left words. Two other
layouts were measured and rejected: logical order placed left to right came back reversed from
PDFium and poppler, and visual order came back reversed from pdfminer.six.

In a right-to-left line the space after a word sits to its left, and words are spaced when the
next word starts further left.

### Rotated and skewed lines

A quad line's text matrix runs along the quad's baseline, with its vertical axis along the
quad's sides, so skew is kept as well as rotation. The font size is the height of the quad
along those sides. Word positions are their quads, or boxes, projected onto the baseline.

### Widths

Every code point advances by one cell, combining marks and joiners included. Grapheme-cluster
widths (zero-width marks through `/W`) were measured and rejected: pdfminer.six then split
Vietnamese, Devanagari and decomposed Hangul words, and PDFium dropped a joiner inside an emoji
sequence. With equal cells all four extractors returned the exact text. Nothing is drawn, so
shaping and font fallback would change no pixels; they are not needed for this font.

`jpdf_page_get_text` returns PDFium's extracted text for a page as UTF-8, so bindings can read a
layer back.

## File structure

- One page with a single `/Contents` stream and a single font resource, `/F1`. OCRmyPDF's graft
  copies the content stream and one font found under `/f-0-0` or `/F1`, and nothing else.
- A Type0 font with Identity-H encoding over a CIDFontType2 whose TrueType program is built in
  code, so no font file is shipped. CIDs are numbered in order of first use, and `/ToUnicode`
  maps each to its code point, including code points outside the BMP. A page can use up to
  65,535 distinct characters.
- Both glyphs are blank: two single-point contours spanning the em box, the shape OCRmyPDF's
  Occulta font uses. They paint nothing in any render mode, and their glyph box is not empty.
  Newer PDFium builds skip text whose glyph box is empty; with a truly empty glyph, a
  one-character CJK word vanished from extraction.
- Streams are Flate-compressed and numbers are written in fixed point, independent of the C
  locale. Equal input gives byte-identical files: there are no timestamps, and `/ID` is a hash of
  the body.
- The file is built in memory, its cross-reference offsets are checked, and it is published
  through an output transaction, so a failure leaves the destination untouched.

## Refused input

| Input | Status |
|---|---|
| Bidi embeddings, overrides and isolates (U+202A to U+202E, U+2066 to U+2069) | `UNSUPPORTED`: they nest across words, which per-word layout cannot honour |
| Unknown flags, both direction flags, a quad flag on a 1.3 struct | `UNSUPPORTED` or `INVALID_ARGUMENT` |
| Quads with no length or height, corners running anticlockwise, sides within about 6 degrees of the baseline, non-finite corners | `INVALID_ARGUMENT` |
| Invalid UTF-8, surrogates, control characters, noncharacters, empty words | `INVALID_ARGUMENT` |
| Zero-height lines, inverted boxes, lines that do not use every word exactly once | `INVALID_ARGUMENT` |
| More than 1,048,576 lines, 2,097,152 words, 16 MiB of text or 65,535 distinct characters | `LIMIT` |
| `image_format` or `png_compression` set in `jpdf_write_options` | `UNSUPPORTED` |

## Evidence

- `api_text_layer` reads layers back through JPDFium's own PDFium. It checks:
  - the page size;
  - text in logical order: accents, combining marks, CJK without separators, and code points
    outside the BMP;
  - blank rendering, and byte-identical output for equal input;
  - 200 repeated writes under LeakSanitizer;
  - rejections, larger caller structs, and a failed write leaving the destination untouched;
  - concurrent writers beside a reader, under TSan;
  - Hebrew, Arabic with harakat, and a Hebrew word in a Latin line read back in logical order;
  - rotated (15 and 90 degrees) and skewed quad lines read back, drawing nothing;
  - 1.3-sized structs still accepted.
- PyJPDFium's `tests/parity/test_multilingual_parity.py` qualifies the general path. Twenty-three
  samples are each written flat, rotated 15, 90 and 180 degrees, and skewed. They cover Latin,
  Greek, Cyrillic, Chinese, Hangul, kana, Devanagari, Thai, combining marks, emoji sequences,
  Hebrew with and without points, Arabic with harakat, Persian with a ZWNJ, and mixed-direction
  lines. Each layer is read by four extractors: JPDFium's PDFium, pypdfium2's newer PDFium,
  pdfminer.six 20260107 and poppler 24.02's `pdftotext`. Every character's box must land in the
  cell the writer contract gives it, and the text must reach the level each extractor showed in
  the qualification run, recorded in PyJPDFium's `docs/COMPATIBILITY.md`. Nine mutations of the
  layout code, among them an unmirrored right-to-left run, a wrong bidi level bound and a
  left-to-right-only line direction, each fail this suite.
- PyJPDFium's `tests/parity/test_text_layer_parity.py` uses independent tools:
  - pypdfium2 5.14.0, which bundles a newer PDFium than JPDFium's pin. It checks the text,
    search across words, and that word spaces are real characters rather than generated ones.
    Character boxes must lie inside their word box and span it edge to edge within 0.05 pt
    horizontally. Vertically the bound is 2% of the font size, because that PDFium rounds glyph
    tops up by about 0.012 em.
  - pikepdf 10.15.0's qpdf syntax check and fontTools 4.64.0, which verifies the table and
    whole-font checksums.
  - OCRmyPDF 17.13.0's own `_graft.py`. After grafting, the page renders pixel-identical to the
    original, and the text, search and placement carry over, including on a `/Rotate 90` page.
    Its `strip_invisible_text`, used by `--redo-ocr`, removes the layer completely.

## OCR module

`libjpdfium_ocr` recognizes text with PaddleOCR's PP-OCR models on ONNX Runtime. It is optional:
the core never depends on it, and it links to the core instead of compiling its own copy of the
domain or the handle table. Recognition works on detached pixels, so it never enters the PDFium
domain. The C API is `native/ocr/include/jpdfium_ocr.h`.

## Pinned inputs

| Input | Pin |
|---|---|
| ONNX Runtime | 1.30.0 CPU packages from the GitHub release, by the digests GitHub publishes (`native/ocr/onnxruntime.version`) |
| Profile `pp-ocrv6-small` | PaddlePaddle's own ONNX exports of PP-OCRv6 small, at fixed Hugging Face revisions, by SHA-256 (`native/ocr/profiles/pp-ocrv6-small.profile`) |
| Dictionary | Extracted from the recognizer's config by `fetch_profile.py`, with a pinned digest |

```bash
bash native/ocr/fetch-onnxruntime.sh linux-x64
python3 native/ocr/tools/fetch_profile.py native/ocr/profiles/pp-ocrv6-small.profile DEST
```

`build-real.sh` builds the module once ONNX Runtime has been fetched (`JPDFIUM_OCR=0` turns it
off). It stages the module and the runtime library, under the name the module links and without
ONNX Runtime's provider library, in `native/dist/ocr-<platform>`, apart from the core bundle, so
the core's size budget and bundle checks are unchanged. A distribution that ships the module
also ships `native/ocr/onnxruntime/LICENSE` and `ThirdPartyNotices.txt`.

Two profiles share the same pinned models:

- `pp-ocrv6-small` uses PaddleOCR 3.7's defaults, so detection runs at the image's full
  resolution, up to 4000 px.
- `pp-ocrv6-small-balanced` caps detection at 1600 px on the longer side. On 300 dpi pages it
  takes about half the time and a third of the memory, with the same accuracy on PyJPDFium's
  benchmark (its `docs/PERFORMANCE.md`).

Each profile matches the official pipeline run with the same settings.

Opening an engine reads every profile file once and refuses it unless its digest matches. The
models are handed to ONNX Runtime from those same bytes. The profile also fixes the pipeline
parameters, and unknown keys are refused.

## Pipeline

The module reproduces PaddleOCR 3.7's general OCR pipeline with orientation classification,
unwarping and text-line orientation turned off, which is its default ONNX Runtime configuration:

1. **Detection input.** DetResizeForTest (minimum side 64, at most 4000, multiples of 32), then
   NormalizeImage on BGR channels.
2. **Boxes.** DBPostProcess with threshold 0.3, box threshold 0.6, unclip ratio 1.5 and at most
   3000 candidates.
3. **Order.** SortQuadBoxes.
4. **Crops.** CropByPolys(quad): the minimum-area rectangle warped upright, then turned 90 degrees
   when tall.
5. **Recognition.** Crops are sorted by aspect ratio and read in batches of six, each batch padded
   to its widest crop, then decoded with CTCLabelDecode over the profile's dictionary.

PaddleOCR's results depend on OpenCV and pyclipper arithmetic. `cv_compat.cpp` ports the OpenCV
4.10 operations involved, and `paddle.cpp` ports Clipper 6.4.2's polygon offset:

- `resize` (`INTER_LINEAR` fixed point);
- `warpPerspective` (`INTER_CUBIC`, `BORDER_REPLICATE`, with its block-relative coordinates);
- `getPerspectiveTransform`, `findContours`, `convexHull`, `minAreaRect`, `boxPoints` and
  `fillPoly`.

Python rounding, float32 arithmetic and numpy's pairwise mean are matched where results depend
on them.

Each line carries a polygon in source pixels, its text, the mean probability of its characters and
its detection score. The models report lines only, so word geometry is marked absent; words are
never invented by splitting a line.

## Handles and errors

Engines and results are module objects in the core's generation-checked table
(`jpdfium_api.h`). A lease keeps an engine alive while a recognition runs, even if it is closed
meanwhile, and a handle of the other kind is `JPDF_E_WRONG_HANDLE_TYPE`. Errors are read with
`jpdf_last_error_message`, as for the core. The module must stay loaded while its objects exist.

Engines are immutable after opening; concurrent recognitions on one engine are supported.

## Parity

PyJPDFium's `tests/parity/test_ocr_parity.py` runs the official `paddleocr` 3.7.0 package on
ONNX Runtime 1.30.0, offline and with the same model files, on eight rendered pages:

- 72 to 600 dpi; gray, RGB and 1-bit;
- several fonts, accented Latin text and a small table;
- a skewed line and a rotated heading;
- a page small enough to be upscaled, and one large enough to be scaled down.

Every polygon and every text is identical. Confidences differ by at most 1.2e-7.

`native/ocr/tests/ocr_geometry.cpp` checks each ported step bit for bit against outputs recorded
from the reference stack by `make_golden.py`.

Vertical text is misread exactly as the reference misreads it: reading it needs the text-line
orientation model, which this profile does not include.

Each claim about the safe API names the level of evidence behind it.

| Level | What runs | Where |
|---|---|---|
| Stub | Java suite against `jpdfium_stub` (no PDFium) | Default CI |
| Unit | `api_object_table`: handle table alone, no PDFium | Every CMake build |

Sanitizers instrument the bridge only. PDFium ships as uninstrumented prebuilt libraries, so a clean
run says nothing about PDFium internals.

## `api_safety` coverage

Lifecycle before and after init, the legacy authority latch, struct-size and flag validation,
stale, fabricated and wrong-type handles, slot reuse, `BUSY` parent close, bitmap and view
ownership across page, document and runtime shutdown, transactional PNG output (budget failure
leaves the destination intact with no staging leftovers), 8-thread renders of independent and
shared documents compared byte-for-byte, a 100-round close race, and shutdown refusal and
finality.

A mutation that replaced the domain mutex with a per-thread lock failed 11 checks (render
mismatches, close-race failures, corrupted accounting), so these tests detect a missing
serializer.

## `api_guards` coverage

Guarded legacy calls refused before init with the refusal reported, one admission per guarded
call, a guarded call from inside a PDFium callback refused as re-entry, ordinary calls refused but
closes admitted while quiescing, resume, legacy and safe-API callers rendering byte-identically
on 8 threads in one process (the Java plus Python case), and bounded shutdown timing out behind a
busy domain.

## `api_text_layer` coverage

Text layers read back through PDFium. The test covers:

- page size, and text in logical order, including combining marks, CJK and code points outside
  the BMP;
- blank rendering and byte-identical output;
- 200 repeated writes under LeakSanitizer;
- input rejections, larger caller structs, 1.3-sized structs, and transactional failure;
- right-to-left, mixed-direction, rotated and skewed lines read back in logical order;
- four concurrent writers beside a reader, under TSan.

Checks with independent tools, including OCRmyPDF's own graft and a four-extractor
multilingual qualification, are in PyJPDFium's parity suite ([TEXT_LAYER.md](#invisible-text-layers)).

## OCR coverage

- `ocr_geometry` checks every ported OpenCV and Clipper step, and PaddleOCR's pre- and
  post-processing, bit for bit against outputs recorded from the reference stack. It needs no
  models.
- `ocr_engine` reads a rendered page through the module. It also covers:
  - engine and result lifetimes, and wrong-type handles;
  - four concurrent recognitions on one engine;
  - a tampered profile being refused.

  It needs a fetched profile in `JPDFIUM_OCR_PROFILE` and is skipped without one.
- `api_image` decodes hand-built PNGs of every colour type.

ONNX Runtime is not instrumented. Under LeakSanitizer one allocation of its own is suppressed, and
under TSan races between its own worker threads are suppressed (`native/ocr/tests/*.supp`).
Nothing in JPDFium's code is suppressed. Parity with the official PaddleOCR pipeline is in
PyJPDFium ([OCR.md](#ocr-module)).

## Running real-native tests locally

```bash
bash native/fetch-prebuilt-pdfium.sh linux-x64
bash native/build-real.sh
ctest --test-dir native/build-real --output-on-failure
```

These steps need a Linux environment; a container works well. The release's asset digests are
listed by `gh api repos/Stirling-Tools/JPDFium/releases/tags/<tag>`.

Sanitized builds need clang (the CMake flag `-shared-libasan` is clang-only) and executables
linked against the same shared runtime:

```bash
CC=clang CXX=clang++ cmake -B build-asan -S native -DJPDFIUM_USE_PDFIUM=ON \
  -DPDFIUM_DIR=$PWD/native/pdfium -DJPDFIUM_SANITIZE=address,undefined \
  -DCMAKE_EXE_LINKER_FLAGS=-shared-libsan
```

TSan needs the `personality` syscall, which Docker's default seccomp profile blocks.
